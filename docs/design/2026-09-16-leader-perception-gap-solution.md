# Leader 感知盲区优化方案(Master 合并版,2026-09-16)

> A = dev-glm(task-34686394,tmail-b81e9e77 + tmail-37a8a729)
> B = dev-deepseek(task-bd5910d2,tmail-9dec6059 + tmail-c3d82a72 补充)
> 两路独立调研,未互看结论;本档由 Master 交叉裁决合并,待用户确认后才进实施。
> 用户痛点原话:①"leader 经常不知道其他成员的运行状态,很多时候成员都停了,leader 也不知道";②"有时候团队成员忘记给 leader 发消息了,任务做完 leader 也不知道"。

## 一、根因(两路独立取证,结论一致)

1. **回合结束信号不通向 leader(痛点 A 根因)**。成员每轮跑完,平台必发 `session:done`;两路逐一核对它的全部消费者(落库 / need_reply / 显式 watch / 秘书 / 自主排班 / 时间线 / UI 广播)——**没有任何一条团队路径把它转成"唤醒 leader"**。用户 UI 看得到成员绿点灭,leader 的上下文里什么都没有。唤醒系统(teamWakeCoordinator)基建本身健全(合并/忙时排队/防丢/线内寻址),**唯一结构缺陷是触发源太窄:只认成员主动汇报**。
2. **完成汇报 100% 靠成员自觉(痛点 B 根因)**。"必须 team.mailbox.send 汇报"只写在成员提示词纪律里;`sessions.ts:271`(BR-03)明文规定"系统不因 session:done 自动改变任务状态";不存在任何"回合结束但本轮无汇报"的检测;一对一消息场景现成的 needReply"平台代提醒"机制,团队派活没有接入。
3. **附带发现的现成 bug(契约自相矛盾)**:leader 提示词教 leader"被唤醒后用 team.mailbox.list / team.task.list 查状态",**但这两个工具对 leader 恒隐藏**——照着做会发现工具不存在;教用的 team.get 又不含任何运行态。
4. **运行态只有 running/idle 两态**:"卡住了"与"干完了"在数据上同为 idle,无法区分。
5. **感知按会话线隔离(B 路补充)**:每个团队恰好一个 leader(平台拒绝第二个);成员在 A 线的进展只唤醒 A 线的 leader 格子——**会话线越多,盲区按线数放大**。

## 二、合并方案(四档,按"先查得到→再有人管→最后兜底"递进)

### P0a 查得到(1.5 人日)——修"想查时查不到"
- 新增只读工具 **`team.status`**(leader 可用):一次返回每成员的聚合视图——各线格子会话的运行态并集(running/idle)、排队深度与在飞、最近 mailbox(时间/类型)、名下任务状态、**距上次汇报多久**。数据源 = listWithRuntimeState + 格子表 + mailbox/task 表;鉴权复用 assertTeamMemberAccess。
- **修契约 bug**:team-prompts 中指向隐藏工具的教法改为指向 team.status;隐藏策略保留(防轮询),工具描述明写调用时机(被唤醒时/用户询问时/总结前)。
- 噪音:零(纯被动查询)。前端零改动。

### P0b 停了有人管(2~2.5 人日)——修"停了没人说"(核心)
- **成员回合结束兜底唤醒**:订阅 session:done,反查格子→会话线→线内 leader 格子,走既有唤醒合并队列。触发条件:**该回合是团队派发/定向回合,且回合期间无任何 mailbox 白名单消息、无任务状态更新**(静默回合才发——正常汇报路径零新增打扰)。
- 唤醒文案三档:①正常结束但没汇报(附成员/任务/最后消息摘要,引导 leader 核对);②stopReason=error(附错误);③cancelled。
- **降噪四件套**(缺一不可):仅当该成员名下有任务在跑才发;复用 15s 合并桶把多成员结束合成一条;每成员每小时限流(建议 6 条,超出降级汇总);系统唤醒产生的回合不算"未汇报"(防 leader 被唤醒→派活→成员回合→再唤醒的 ping-pong 放大)。
- **跨线约束**(B 路补充推导):静默判定与唤醒聚合按团队维度做,不按单线——多线团队不放大盲区。
- 漏报边界:进程崩溃/事件缺失路径本档不覆盖(交 P2);纯静默回合恰逢重启窗口丢一次,记入已知限制。

### P1 顺手项(~1 人日)
- **欠汇报代提醒(推成员不推 leader)**:回合结束仍未汇报 → 平台给**成员**注入系统提醒"本轮尚未提交汇报,请补交结果或标记 blocked"(复刻 needReply 代提醒模式)。leader 收到的就是正式汇报而非系统噪音;与 P0b 互补(P0b 事后告知,P1 事中催办)。
- **提示词引导**:leader 提示词补一句——派活后可用 agent.session.watch 盯成员格子、可用 team.status 查实时状态(机制现成,纯文案,零风险)。
- **补团队任务的 watch 触发点**:让会用 agent.task.watch 的 leader 对团队任务也有统一语义(现对团队任务空转)。

### P2 兜底(3~4 人日,视 P0b 噪音数据再定)
- **停滞扫描 digest**:周期扫描(60s~5min 可配)在跑任务名下的成员——上次汇报超时 / running 但无进展超时(复用现成 watchdog 判定,它现在只写日志无出口)/ idle 但任务在跑超时——只对**异常**成员发聚合摘要。这是事件链全部失效(含崩溃)时的最终兜底,常态零噪音。

## 四、风险与边界(两路合并)

1. 噪音反噬比漏报更伤信任——P0b 四件套缺一不可,上线后按实测调参。
2. 唤醒 ping-pong 必须排除(系统唤醒回合不计入"未汇报")。
3. 文案必须写"回合结束"而非"任务完成"(回合结束≠完成,防 leader 重复派活/误报用户)。
4. 崩溃路径 session:done 可能缺失——只有 P2 扫描能兜,本方案不承诺覆盖崩溃。
5. 全部方案只做"通知/查询",不碰 BR-03(系统不自动改任务状态)的既有边界。
6. 隐藏工具策略的常量在两处副本解析,改动需同步(已列为实施注意点)。

**P0a + P0b + P1 一期做完(≈ 4.5~5 人日)**:P0a 便宜且修现成 bug;P0b 直接治两个痛点;P1 让闭环更克制。P2 等 P0b 上线观察噪音数据再决定。
