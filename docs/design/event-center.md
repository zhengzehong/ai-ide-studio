# 事件中心设计

## 背景

AI IDE Studio 当前以任务和 Agent 协作为核心。任务适合表达已经决定要处理的工作，但很多真实场景的问题在于：人需要先发现信息、判断价值、整理成任务、再分派给 Agent。

事件中心要解决的是任务之前的发现和分发问题。它让系统、定时任务、外部触发器和 Agent 能主动记录“发生了什么”或“发现了什么”，再由人、规则或订阅 Agent 决定是否消费、忽略或转成任务。

## 定位

事件中心是一个可分类、可订阅、可消费的事件 Inbox。

事件表示“发现了一件可能值得关注的事情”。任务表示“已经决定要交付的工作”。事件可以很多、可以被忽略、可以只进入日报；任务应该更少、更明确，并有负责人、状态和完成标准。

```text
系统 / 定时任务 / Agent / 外部触发器
  -> 写入事件
  -> 分类、去重、打分
  -> 人确认或订阅 Agent 消费
  -> 可能转成任务、会话、报告或归档
```

## 核心原则

- 事件不是任务。事件是信号、线索、机会或候选工作；任务是承诺要处理的工作。
- 事件类别必须预定义。AI 不能随意发明类别，避免事件流失控。
- 事件表结构固定，类别数据放入动态 JSON。不同类别通过 `payload_json` 和类别 schema 表达差异，不为每个类别新增数据库列。
- AI 可以写事件，也可以消费事件，但必须受类别权限、频率限制和消费规则约束。
- 自动化默认保守。低风险事件可以自动消费，高风险事件需要人工确认。
- 事件消费必须可追踪。谁消费、什么时候消费、结果是什么、是否转任务，都应该留下记录。

## 核心概念

### 事件类别

事件类别定义事件的业务含义、动态数据结构、写入权限和消费权限。

示例类别：

- AI 热门项目
- AI 趋势
- 代码提交
- 测试失败
- 功能完成
- 安全风险
- 产品反馈
- 任务候选
- 发布素材
- 日报素材

类别可以由用户创建或停用，但事件写入时只能选择已有类别。类别包含一个 JSON schema 或表单定义，用于校验和渲染该类别的 `payload_json`。

### 事件

事件是固定字段加动态 payload 的记录。

固定字段用于列表、筛选、权限和状态管理，例如标题、摘要、类别、来源、优先级、置信度、状态、标签、去重 key、创建时间。

动态字段放入 `payload_json`，由类别定义解释。

`AI 热门项目` 的 payload 示例：

```json
{
  "projectName": "ExampleAI",
  "githubUrl": "https://github.com/example/example-ai",
  "stars": 12800,
  "starsDelta": 2300,
  "hotReason": "过去 24 小时增长很快，多个 AI Agent 社区提到",
  "relatedTech": ["Agent", "RAG", "Workflow"],
  "recommendedAction": "建议分析架构和可复用点"
}
```

`代码提交` 的 payload 示例：

```json
{
  "repo": "ai-ide-studio",
  "branch": "prd",
  "commit": "13245b2",
  "message": "fix: clear live plan after turn completion",
  "author": "Codex",
  "changedFiles": 5,
  "recommendedAction": "生成变更摘要并检查是否需要发布说明"
}
```

### 订阅规则

订阅规则定义哪些事件应该被谁消费，以及采用什么动作。

规则可以按类别、项目、来源、优先级、标签、置信度和 payload 字段过滤。

动作模式：

- 仅入库：事件只进入事件中心。
- 自动总结：订阅 Agent 消费事件并写回摘要。
- 待确认转任务：AI 给出建议，人确认后转任务。
- 自动转任务：符合条件后直接创建任务。
- 自动执行：低风险事件直接触发订阅 Agent 会话。

### 消费记录

一个事件可以被多个订阅或 Agent 消费。事件本身有全局状态，消费记录保存每个消费者的状态和结果。

示例：

- 趋势 Agent 消费 AI 热点事件并生成摘要。
- PM Agent 消费同一事件并判断是否转任务。
- 日报 Agent 消费同一事件并收进日报素材。

消费记录避免“一个事件只知道已消费，但不知道谁消费了、结果是什么”的问题。

## 事件状态

事件看板面向用户展示的状态：

- 未处理：事件刚写入，尚未被忽略、消费或转任务。
- 处理中：已有订阅 Agent 正在消费。
- 已消费：事件已被消费，暂无正式任务。
- 已忽略：用户或规则判定不处理。
- 已转任务：事件已创建或关联任务。
- 已归档：事件不再出现在默认列表。

消费记录的状态：

- pending
- claimed
- running
- succeeded
- failed
- skipped

## 三个产品页面

### 事件中心

事件中心类似收件箱和看板。

主要区域：

- 左侧分类：全部、未处理、处理中、已消费、已忽略、已转任务、已归档、我的订阅。
- 中间列表：事件卡片，展示标题、摘要、类别、来源、优先级、置信度、标签、消费状态。
- 右侧详情：动态 payload、证据来源、消费记录、关联任务、关联会话和操作按钮。

常用操作：

- 忽略
- 归档
- 交给 Agent
- 转成任务
- 关联已有任务
- 查看消费结果
- 重新触发消费

### 事件类别管理

类别管理用于定义允许进入事件中心的事件类型。

管理内容：

- 类别名称和 key
- 描述
- payload schema 或表单定义
- 默认优先级
- 允许写入的 Agent、系统源或外部源
- 允许消费的 Agent
- 是否启用

类别管理的目标不是把所有字段变成数据库列，而是给 `payload_json` 提供稳定解释和校验。

### 订阅规则

订阅规则定义事件如何被消费。

管理内容：

- 规则名称
- 事件类别
- 过滤条件
- 消费 Agent
- 动作模式
- 是否自动执行
- 是否需要人工确认
- 频率限制和失败重试策略

规则应该支持试运行，让用户能看到当前规则会匹配哪些历史事件。

## Agent 工具

事件中心必须作为平台工具暴露给 AI。

基础工具：

- `event.category.list`：列出当前 Agent 可见的事件类别。
- `event.create`：写入事件。
- `event.list`：查询事件。
- `event.get`：查看事件详情。
- `event.claim_next`：领取下一个可消费事件。
- `event.consume`：提交消费结果。
- `event.convert_to_task`：把事件转成任务。
- `event.ignore`：忽略事件。

工具权限由类别和 Agent 权限共同控制。AI 只能写入被允许的类别，只能消费匹配订阅或权限的事件。

## 典型闭环

### AI 热门项目发现

```text
定时任务触发 AI 热点采集 Agent
  -> Agent 搜索并发现热门项目
  -> 调用 event.create 写入 AI 热门项目事件
  -> 订阅规则匹配到 AI 项目分析 Agent
  -> 分析 Agent 消费事件并写回价值评估
  -> 用户查看事件，决定是否转成正式任务
```

### 代码提交处理

```text
系统或 Agent 记录 commit 事件
  -> Release Note Agent 订阅代码提交事件
  -> 自动生成变更摘要
  -> 若包含风险标签，再交给测试 Agent 或创建验证任务
```

### 任务候选发现

```text
代码审查 Agent 发现一个潜在问题
  -> 写入任务候选事件
  -> PM Agent 或用户确认是否值得处理
  -> 确认后转成任务并分派给合适 Agent
```

## 安全和噪音控制

事件中心需要防止噪音和自动化循环。

必要约束：

- 类别白名单：AI 只能写入已有类别。
- payload 校验：写入时按类别 schema 校验。
- 去重 key：相同来源和业务对象的事件合并或降噪。
- 频率限制：限制 Agent 和外部源的写入速率。
- 置信度：AI 发现类事件必须给出置信度和证据。
- 消费幂等：同一订阅不能无限重复消费同一事件。
- 自动化等级：高风险动作默认需要人工确认。
- 审计记录：写入、消费、忽略、转任务都应可追踪。

## 和现有系统的边界

- 事件中心不替代任务。事件可以转任务，但默认不是任务。
- 事件中心不替代 `session_events`。`session_events` 是对话内部事件源，用于历史恢复和诊断。
- 事件中心不替代 `team_events`。`team_events` 是 Team 内部上下文事件。
- 事件中心可以复用规则、定时任务、Agent、Session、Task 和 Team 能力。

推荐关系：

```text
rules / schedule 负责触发
Agent / system 负责生产事件
Event Center 负责存储、分类、订阅、分发
Session 负责具体执行过程
Task 负责正式工作项追踪
Team 负责多 Agent 协作
```

## 非目标

第一版不追求完整消息队列能力，不做分布式 Kafka 式事件总线，不做复杂外部 webhook 市场，不默认允许 AI 自动创建高风险任务。

第一版目标是让用户能定义类别，AI 能写入事件，事件能进入看板，订阅 Agent 能消费，消费结果能回写，必要时能转成任务。
