# ACP Diff 文件变更功能设计

## 1. 设计目标

这个功能的目标是：在对话过程中，让用户能清楚看到 Agent 本轮对哪些文件做了修改，并能按需查看修改详情。

它解决的是两个问题：

1. 用户需要知道“这一轮 Agent 改了哪些文件”。
2. 用户需要在不打断对话体验的情况下，快速展开查看 diff。

这个功能不追求一开始就做复杂的文件审计、全量文件监听或回滚系统。第一版只基于 ACP runtimes 上报的 `diff` 信息，做一个稳定、轻量、和对话体验一致的文件变更展示。

## 2. 核心口径

### 2.1 文件变更是什么

在本功能里，“文件变更”指：Agent runtime 通过 ACP 工具调用内容上报的 `diff`。

也就是说：

```text
文件变更 = ACP diff 上报过的文件修改
```

它表达的是“Agent 告诉平台它修改了这些文件”，不是平台自己扫描文件系统得出的完整审计结果。

### 2.2 什么不算文件变更

以下内容不直接算作文件变更：

- 工具调用里的 `locations`。
- grep、read、search 这类读文件行为。
- 终端命令输出里提到的文件名。
- Agent 文本回复里说“我修改了某文件”。
- Shell 脚本、第三方 MCP、外部程序私下修改文件但没有上报 ACP diff 的情况。

`locations` 只能说明工具访问或关联了某些文件位置，不代表文件一定被修改，所以不能用它当作“已修改文件”的依据。

## 3. 能力边界

### 3.1 适合做什么

ACP diff 适合做：

- 本轮改动文件列表。
- 本轮 diff 摘要。
- 对话气泡里的“修改文件 N 个”。
- 点击展开查看每个文件的 diff。
- 后续 review 功能的上下文入口。

### 3.2 不适合做什么

ACP diff 第一版不适合直接做：

- 可靠回滚。
- 全量文件系统审计。
- 多 Agent 并行写入冲突判定。
- 判断工作区当前真实状态是否仍和 diff 一致。
- 识别 shell、脚本、外部工具造成但未上报的文件变化。

如果后续要做回滚，应该单独设计 checkpoint 或 Git 工作区快照。不要把“显示 Agent 上报的 diff”和“保证可回滚”混成一个功能。

## 4. 用户看到的效果

### 4.1 当前正在执行的一轮

当用户发送消息后，当前 Agent 回复气泡仍按既定对话规则显示：

```text
<执行过程>
  正在思考
  工具调用
  文件修改
  工具调用
</执行过程>

最终回复
```

如果运行过程中收到 ACP diff，执行过程里出现一个“文件修改”块。

示例：

```text
执行过程

  工具调用：Edit
  文件修改：2 个文件
    - src/acp/host.ts
    - ui/src/components/chat/ChatView.tsx

最终回复

  已修复对话流式展示问题，并补充了测试。
```

当前正在执行的一轮里，文件修改可以实时出现。用户不需要等整轮结束才知道 Agent 改了文件。

### 4.2 当前轮完成后

当前轮完成后，执行过程默认折叠。气泡底部保留轻量摘要：

```text
耗时 1m 24s · 输入 12.3k · 输出 1.8k · 修改文件 2 个
```

用户点击“修改文件 2 个”或展开执行过程，可以看到：

```text
修改文件

  M src/acp/host.ts
  M ui/src/components/chat/ChatView.tsx
```

继续点击某个文件，显示该文件的 diff 详情。

### 4.3 历史消息

历史消息不应该一次性加载大段工具详情和完整 diff。

进入会话时，历史消息只显示轻量摘要：

```text
执行过程 · 已折叠
最终回复正文
耗时 1m 24s · 修改文件 2 个
```

用户点击后，再加载执行过程和 diff 详情。

这样可以避免长会话卡顿，也能保持历史对话快速打开。

## 5. 前端展示设计

原型文件：`prototypes/acp-diff-file-changes.html`，用浏览器打开可看到完整交互效果。

### 5.1 展示位置

文件变更在对话气泡里有三个出现位置：

1. **执行过程内的文件修改卡片** — 按真实事件顺序，紧跟在对应的工具调用之后。
2. **气泡底部的独立文件变更卡片** — 完成后汇总本轮所有修改，可展开查看详情。
3. **气泡底部摘要行** — 一行文字，快速告知有无改动。

### 5.2 文件变更卡片（FileChangesCard）

文件变更卡片是核心 UI 组件，结构如下：

```text
┌─────────────────────────────────────────────────┐
│ 📄  已编辑 2 个文件                  查看变更 │
│      +24  -8                                    │
├─────────────────────────────────────────────────┤
│  M  src/stores/session.store.ts       +15 -6  ▶ │
│  M  ui/src/components/ChatView.tsx     +9 -2  ▶ │
└─────────────────────────────────────────────────┘
```

组件分为三个区域：

**头部**：左侧图标 + 标题 + 增删行数统计 + 右侧查看/收起入口。

- 标题格式：`已编辑 2 个文件` 或 `已编辑 2 个文件 · 新增 1 个文件`。
- 统计行格式：绿色 `+24` 红色 `-8`。
- 点击「查看变更」展开文件列表，展开后显示「收起变更」。

**文件列表**：每行一个文件，包含：

- 变更类型徽章：`M`（黄底）/ `A`（绿底）/ `D`（红底）。
- 文件路径：等宽字体显示。
- 增删行数：`+15 -6`。
- 展开箭头：点击展开该文件的 diff 详情。

**Diff 详情面板**：点击文件行后在其下方展开，深色背景，显示 unified diff：

- 绿色行表示新增。
- 红色行表示删除。
- 灰色行表示上下文。
- 左侧显示行号。

### 5.3 变更类型判断

| 标记 | 含义 | 徽章颜色 |
|------|------|----------|
| A | 新增文件 | 绿底绿字 |
| M | 修改文件 | 黄底黄字 |
| D | 删除文件 | 红底红字 |
| ? | 无法判断 | 灰底灰字 |

判断规则：

- 没有旧内容，只有新内容 → 新增。
- 有旧内容，新内容为空 → 删除。
- 旧内容和新内容都存在 → 修改。
- 信息不足 → 未知。

### 5.4 三个场景的展示行为

**场景 1：当前轮实时生成中**

执行过程默认展开。每次收到 ACP diff，在执行过程对应位置插入一个小型文件变更卡片。用户实时看到 Agent 修改了哪些文件。

**场景 2：当前轮完成后**

执行过程折叠。气泡底部显示完整的文件变更卡片和摘要行。

**场景 3：历史消息**

历史消息默认不加载完整 diff。只显示摘要行「📁 修改文件 N 个」。用户点击后再按需加载文件列表和 diff。

### 5.5 和执行过程的关系

文件修改卡片是执行过程的一种块类型（`processBlock.kind = 'fileChange'`），按真实事件顺序出现。不允许把所有文件变更合并到执行过程末尾或最终回复上方。

### 5.6 底部摘要行

摘要行格式：`⏱ 耗时 · 📥 输入tokens · 📤 输出tokens · 📁 修改文件 N 个`

- 如果本轮没有文件变更，不显示文件相关部分。
- 「修改文件 N 个」可点击，滚动到文件变更卡片。
- N 是去重后的文件数。

### 5.7 组件层级

```text
ChatBubble
├── ProcessBlock[]（执行过程，按事件顺序）
│   ├── ThinkingBlock
│   ├── ToolCallBlock
│   ├── FileChangesCard（小型）              ← 新增
│   ├── NoteBlock
│   └── ...
├── FinalAnswer（最终回复）
├── FileChangesCard（完整版，可展开）        ← 新增
└── BubbleFooter（摘要行）
```

## 6. 数据流逻辑

### 6.1 实时阶段

实时阶段以前端收到的 `session:update` 为准。

当收到工具调用更新时：

1. 检查工具调用内容里是否有 `type = diff`。
2. 如果有，把它归入当前 Turn 的执行过程块。
3. 同时更新当前 Turn 的文件变更摘要。
4. 如果同一个文件多次出现，摘要里合并成一个文件，但执行过程仍保留真实顺序。

也就是说：

```text
执行过程看顺序
摘要看去重后的文件数
```

### 6.2 持久化阶段

后端仍把工具调用、执行过程、最终消息按现有对话机制保存。

文件变更摘要可以从已保存的工具调用内容里提取，也可以作为轻量摘要字段保存。推荐长期方向是保存轻量摘要，因为历史会话列表不应该每次都解析完整工具 JSON。

第一版可以先做到：

- 当前轮：从实时事件里提取。
- 历史轮：展开执行过程时再从持久化工具调用里提取。

如果性能不够，再补轻量摘要字段。

### 6.3 切换会话和刷新

切换会话或刷新页面后：

1. 先加载 `messages`，展示最终回复和摘要入口。
2. 如果消息有文件变更摘要，直接显示“修改文件 N 个”。
3. 如果没有摘要但有执行过程，先显示“执行过程”，用户展开后再加载 diff。
4. 加载执行过程时，按事件顺序恢复文件修改块。

不能为了显示文件变更，在进入会话时一次性加载所有历史工具详情。

## 7. 和 Git / Review / 回滚的关系

### 7.1 和 Git diff 的区别

ACP diff 和 Git diff 不是一回事。

ACP diff：

```text
Agent 本轮上报了什么修改
```

Git diff：

```text
当前工作区相对 Git 基线有什么修改
```

如果用户或另一个 Agent 同时改了文件，Git diff 会混在一起；ACP diff 更适合展示“本轮 Agent 报告的改动”。

### 7.2 和 Codex /review 的关系

Codex 的 `/review` 更像是对当前工作区或目标 diff 做审查。它适合作为后续能力：用户点击“审查本轮修改”，平台把本轮 ACP diff 或当前 Git diff 作为上下文交给 Agent。

第一版不把 review 做进文件变更展示里，只预留入口即可。

### 7.3 和回滚的关系

第一版不做回滚。

原因是：ACP diff 只能说明 Agent 上报的补丁，不保证当前文件仍处于可直接反向应用的状态。尤其是多 Agent 并行、用户手动编辑、脚本批量修改时，直接用 diff 回滚容易误伤。

如果后续要做回滚，建议单独做“检查点”：

- 开始任务前创建 checkpoint。
- Agent 执行后展示 checkpoint diff。
- 用户确认后可以回到 checkpoint。

这个能力可以基于 Git，也可以基于平台自己的文件快照，但它是独立功能，不属于本设计第一版范围。

## 8. 异常和兜底

### 8.1 没有 ACP diff

如果本轮没有任何 ACP diff：

- 不显示“修改文件 0 个”。
- 不显示空的文件修改块。
- 只正常显示执行过程和最终回复。

### 8.2 只有 locations

如果只有 `locations`，没有 `diff`：

- 不显示为文件修改。
- 可以在工具详情里显示为“关联文件”或“访问位置”。
- 不计入“修改文件 N 个”。

### 8.3 Diff 内容太大

如果 diff 很大：

- 摘要仍显示文件路径。
- 详情默认折叠。
- 点击文件后再加载完整内容。
- 超大内容可以截断，并提示“内容过大，仅显示前一部分”。

### 8.4 同一文件多次修改

同一轮里同一文件多次出现 diff：

- 执行过程按时间显示每次修改。
- 底部摘要只计为 1 个文件。
- 文件详情里可以显示多段 diff。

## 9. 第一版推荐范围

第一版只做四件事：

1. 从 ACP diff 提取文件路径和变更类型。
2. 当前 Turn 实时显示文件修改块。
3. Agent 气泡底部显示“修改文件 N 个”。
4. 历史消息按需展开查看文件列表和 diff。

暂时不做：

- 自动回滚。
- Git checkpoint。
- 文件 watcher。
- 多 Agent 写入冲突检测。
- side-by-side diff 高级编辑器。

这样实现最小，但方向正确，后续可以自然扩展。

## 10. 判断功能是否成功

这个功能做好后，用户应该能回答三个问题：

1. 这一轮 Agent 有没有改文件？
2. 改了哪些文件？
3. 每个文件大概改了什么？

同时系统不应该引入新的误导：

- 不把读文件当成改文件。
- 不把 locations 当成修改依据。
- 不承诺 ACP diff 覆盖所有真实文件变化。
- 不在历史会话加载时一次性拉取大量工具详情导致卡顿。

一句话：第一版要做的是“对话里的本轮文件修改可见”，不是“一套完整版本控制系统”。
